# ADR-0030: Browser automation for tests: Playwright, replacing puppeteer-core/chrome-launcher

Status: decided 2026-09-14. Narrower than it sounds: only the "what drives a real browser in a test" question. ADR-0029's Lighthouse decision (the `lighthouse` CLI, its own `chrome-launcher`-based browser discovery, `ubuntu-latest`'s preinstalled Chrome) is unchanged and **not** superseded — that is a static accessibility audit, not browser-driven interaction, and stays exactly as ADR-0029 decided it.

## Context

PR #114 added `web/src/app/r/[slug]/submit.e2e.test.ts` to reproduce a production incident that only a real browser driving a real Next server could catch (a `"use server"` module with a non-async export throws at Next's action-dispatch time, which vitest imports, Lighthouse GETs, and `next build`'s compile step all miss). It reached for `puppeteer-core` + `chrome-launcher` because those were already `web/`'s `devDependencies` for ADR-0029's Lighthouse gate — a reasonable reuse in the moment, but no ADR ever decided "puppeteer is how this repo drives a browser in a test"; it was inherited from an unrelated dependency, not chosen for the job.

That incidental choice is now a liability for #26, which needs more than one page load:

- **#26's acceptance criterion is multi-identity**: "org A's session cannot read org B's data" needs two independent, isolated browser identities open at once, asserted against each other in the same test run. Puppeteer has no first-class concept of an isolated browsing context; the workaround is separate `Browser` instances or manually-managed cookie jars, both more code than the property being tested.
- **`storageState`** (Playwright's serializable capture of cookies + `localStorage` for a context) makes "start this test already signed in as a seeded staff member" a one-line fixture instead of driving a real OAuth consent screen (which isn't automatable here at all — see ADR-0031's Trap 5 reasoning) or hand-rolling cookie-jar plumbing per test.
- **This VPS's only Chrome is snap-packaged** (`/usr/bin/chromium-browser` wraps `snap run chromium`) and cannot be launched as a plain child process outside snap's confinement (`Error: Failed to launch the browser process ... not a snap cgroup`). #114's workaround was `PUPPETEER_EXECUTABLE_PATH`, pointed at a separately-downloaded, non-snap Chrome build kept out of the repo — a local-only escape hatch that every future contributor on this VPS has to rediscover for themselves. Playwright ships its own unconfined Chromium (`playwright install chromium`, downloaded once, not launched through the OS package manager), so the escape hatch has nothing left to work around.

Cost to record honestly, not just the benefits: this adds a second test runner alongside vitest (`@playwright/test` has its own CLI, config file, and reporter — it does not run inside `vitest run`), and CI grows a browser-binary download step beyond what `ubuntu-latest`'s preinstalled Chrome already covers for Lighthouse. Both are accepted below.

## Decision

- **`@playwright/test` (pinned `1.63.0`) replaces `puppeteer-core` and `chrome-launcher` in `web/`'s `devDependencies`.** Both removed in the same PR that adds Playwright — no dual-maintenance period, since exactly one file (`submit.e2e.test.ts`) used them and it moves in this PR.
- **Playwright is a second, separate test runner**, invoked via `playwright test`, with its own config (`web/playwright.config.ts`) and its own npm script (`test:e2e`). It does not run inside `vitest run` and vitest does not run inside it — `web/package.json`'s `test` script (vitest) and `test:e2e` script (Playwright) stay two commands, wired as two separate CI steps (`ci.yml`'s `web` job), each asserting its own "nothing silently skipped" gate. A Playwright suite that executes zero tests must fail CI exactly as a self-skipping vitest suite does (`docs/review-rubric.md`); Playwright's own JSON reporter's `stats.expected` count is what that assertion reads, since Playwright has no `numPendingTests`/`numTodoTests` fields to borrow vitest's pattern from directly.
- **`web/src/app/r/[slug]/submit.e2e.test.ts` migrates to Playwright** in this PR, moved to `web/e2e/submit.spec.ts` (Playwright's default `testDir`/`testMatch` convention, kept separate from vitest's `*.test.ts` glob so neither runner picks up the other's files by accident). It keeps every property #114 established: a real `next build` plus the real standalone `server.js` (not `next dev`/`next start`), the real Turnstile widget against Cloudflare's always-pass test key `1x00000000000000000000AA`, loopback-only binding, and the exact regression assertion (no 500 from the action-dispatch request, a real row lands in Postgres). None of that rigor is weakened by the runner swap — it is a mechanical port from Puppeteer's API to Playwright's.
- **The cross-org isolation test for #26** (`web/e2e/cross-org-isolation.spec.ts`) is new in 26a, not a port, and is exactly the case Playwright's browser contexts exist for: two `browser.newContext()`s in one test, each with its own `storageState`, each asserting it can see its own org's queue and not the other's.
- **Downloaded, not system Chrome.** `playwright install chromium` (via `web/package.json`'s own `postinstall` or an explicit CI step — implementation detail, not a design point this ADR fixes) fetches Playwright's own build, unconfined, both on this VPS and in CI. No `PUPPETEER_EXECUTABLE_PATH`-shaped override is needed or provided.

## Consequences

- `web/package.json` gains `@playwright/test` (pinned exact version, matching the ADR-reference-per-dependency rule in `AGENTS.md` — this ADR is that reference) and loses `puppeteer-core`/`chrome-launcher`.
- CI's `web` job grows a browser-install step and a second test-and-assert-nothing-skipped step, alongside vitest's existing one. Both need the same chart-pinned Postgres service container and the same real-build discipline `submit.e2e.test.ts` already required.
- A contributor running Playwright locally for the first time needs `pnpm --filter @frontdesk/web exec playwright install chromium` once; documented in `web/README.md` alongside the existing local-verification notes for the old Puppeteer path (removed).
- The revisit trigger: none anticipated. If Playwright's bundled Chromium ever becomes unlaunchable on a future VPS the way the snap-packaged system Chrome was, the same class of fix (an explicit, documented local override) would apply, but Playwright's stated purpose is exactly to avoid depending on whatever browser happens to be on the host.

## Rejected

- **Keep puppeteer-core, add a second `Browser` instance per identity for the cross-org test.** Works mechanically, but there is no first-class isolated-context primitive to reach for, so the test would be inventing by hand (two `Browser.launch()` calls, no shared `storageState` concept) something Playwright provides as an API. Doesn't remove the snap-Chromium escape hatch either.
- **Puppeteer with `@puppeteer/browsers`' own downloadable-Chrome CLI** (`node .../main-cli.js install chrome@stable`), which is in fact what local verification used ad hoc before this ADR. Solves the snap problem alone, but is a manually-invoked side tool with no first-class npm dependency, config, or CI wiring — exactly the "incidental, undocumented" shape this ADR exists to replace, and still leaves the multi-context problem unsolved.
- **Selenium / WebDriver.** Older API, no built-in isolated-context primitive comparable to Playwright's, and no existing dependency in this repo to build on (this repo has never used WebDriver-based tooling).
- **Skip browser automation for the cross-org test; assert isolation at the RLS/query layer only** (as `db/src/rls.test.ts` already does for the database itself). Real and valuable, but not what #26's acceptance criterion asks for — it names a browser-driven, two-session proof of the same property one layer up (proxy/layout/Server-Action guard, session cookie scoping, the actual staff-facing surface), which a SQL-level test cannot exercise.
