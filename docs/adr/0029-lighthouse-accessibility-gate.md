# ADR-0029: Lighthouse accessibility gate runs per-PR, blocking, via the `lighthouse` CLI against a real `next build`/`next start`; no LHCI server

Status: decided 2026-09-14. Implements 27b's Lighthouse accessibility >= 90 acceptance criterion (#27, ADR-0027 §2).

## Context

27b's brief names a number and nothing else: "Lighthouse accessibility >= 90." Nothing in `.github/workflows/` or any `package.json` runs Lighthouse, axe, or pa11y today - this PR is the first to add a page (`/r/<slug>`, the landing page) worth gating at all. Left unstated: does it block a merge or just report; does it run on every PR or on a schedule; what does it actually point Lighthouse at (a dev server, a production build, a deployed URL); and does it need a database behind the pages it audits (both new pages read live org/queue data). A gate with no mechanism is not a gate - the same failure ADR-0025 and ADR-0027 both named for their own issues.

Facts checked before deciding:

- **`web/`'s two new public surfaces are exactly what needs auditing.** `/r/<slug>` is a real form (labels, required fields, a third-party Turnstile widget); `/` (the landing page) is prose plus that same form plus a live queue list. Neither existed before this PR - `/t/[token]` (27a) is unauthenticated too but has no form and was already shipped without this gate.
- **Lighthouse's `accessibility` category is a static/DOM audit, not a timing measurement.** Unlike `performance` (CPU-throttling-sensitive, notoriously flaky on shared CI runners), accessibility scoring checks markup/ARIA/contrast/labeling - deterministic for a given rendered DOM. This is the material fact that makes "blocking, per-PR" viable where a performance budget would not be.
- **GitHub's `ubuntu-latest` runner image ships Google Chrome preinstalled** (documented in the image's own software manifest) - `chrome-launcher` (which the `lighthouse` CLI uses internally) auto-discovers it, no separate browser-install action needed. Confirmed locally too: this VPS has `chromium-browser` and `google-chrome`-family binaries already present, and `npx lighthouse --version` resolves and runs without any extra setup.
- **Both new pages need a live Postgres to render meaningfully.** `/` needs a demo org and (ideally) queue rows to audit the non-empty state, not just the empty one; `/r/<slug>` needs a real org to look up or it 404s. A gate that audits a 404 page's accessibility is not auditing the form.
- **This repo already has 15 CI checks.** A 16th that needs a service container, a production build, and a headless-browser run is real added cost, not a free addition - worth deciding deliberately rather than bolting onto an existing job.

## Decision

**A new job, `lighthouse`, in `.github/workflows/ci.yml`** - not folded into `web` (that job's Postgres service and migrate/seed steps are reused, but a browser-driven audit is a different failure mode than a vitest run, and `provider-parity`'s precedent is to give a distinct acceptance criterion its own named check in the PR's status list rather than burying it inside a broader job).

- **Runs on every PR, and blocks merge.** Per the "static audit, not a timing budget" fact above: accessibility scores don't have the render-to-render jitter that would make a performance gate a bad blocking check on shared runners. F16/F1's "Lighthouse accessibility >= 90" is written as an acceptance criterion with a number, the same as the eval gate's recall@5 - where a number is stated and measurable, this repo enforces it, not reports it.
- **Points the `lighthouse` CLI at a real `pnpm --filter @frontdesk/web build && pnpm --filter @frontdesk/web start`** (production build and server, port 3000), not `next dev` - matching what actually ships, and cheap: the build step this job needs is the same one `node`'s "Build web" step already proves succeeds, just re-run in this job's own runner (cross-job artifact sharing was considered and rejected below).
- **Backed by the same chart-pinned Postgres service container** `db`/`api`/`python`/`web` already use, migrated and seeded the same way, so the demo org and its queue are real seed data, not a fixture invented for this job alone.
- **Audits exactly two URLs**: `http://localhost:3000/` (the landing page) and `http://localhost:3000/r/<demo-slug>` (the public form, slug read from the seeded demo org rather than hardcoded) - the two pages this PR actually adds. `/t/[token]` is out of scope: it shipped in 27a without this gate, and adding it now is a separate, uncoupled decision this ADR doesn't make.
- **Category scoped to `accessibility` only** (`--only-categories=accessibility`) - performance/SEO/best-practices are not what 27b's acceptance criterion names, and including them would import exactly the CPU-throttling flakiness this decision's blocking status depends on avoiding.
- **Threshold: score `>= 0.90`** (Lighthouse reports 0-1; the CLI's own JSON output is parsed and compared in the workflow step, no separate assertion tool). Exactly F16's number, nothing looser.
- **Tool: the plain `lighthouse` npm CLI** as a `web/` devDependency (pinned, like every other dependency in this repo), not `@lhci/cli`. Lighthouse CI's added value over the bare CLI - a hosted or self-run results server, historical trend storage, GitHub status-check integration beyond a plain job pass/fail - is infrastructure this gate doesn't need: one number, compared once, per PR. The plain CLI's own `--output=json` plus a `node -e` one-liner (the same pattern api's/worker's "assert nothing skipped" steps already use) is the whole assertion.

## Consequences

- `web/package.json` gains `lighthouse` as a devDependency (pinned exact version, matching the ADR-reference-per-dependency rule in AGENTS.md - this ADR is that reference), invoked as `pnpm --filter @frontdesk/web exec lighthouse <url> ...` so the same pinned binary runs identically in CI and on a laptop. Deliberately `exec`, not a `package.json` script run via `pnpm run ... -- <args>`: verified locally that the latter's extra layer of shell re-parsing corrupts a quoted multi-flag value like `--chrome-flags="--headless=new --no-sandbox"` (Chrome then launches without `--headless` and fails for lack of a display) - `pnpm exec` invokes the local binary directly with no such rewriting.
- CI grows to 16 checks. Accepted: a numeric, stated acceptance criterion this repo has the means to enforce is exactly the category of check worth adding, per the same reasoning the eval gate and provider-parity already established.
- A future page added to `web/`'s public surface is not automatically audited - this ADR names two specific URLs, not "every route." Extending the list is a small workflow diff, not a redesign.
- If Lighthouse's accessibility scoring ever becomes measurably flaky in this CI environment (not observed; the working assumption above is that it won't be), the fallback the "Rejected" section names is report-only with a required human look, not silently dropping the gate.

## Rejected

- **`@lhci/cli` with a results server (temporary public storage or self-hosted).** Adds a service (or a network call to Google's temporary-storage server) and a config format (`lighthouserc.js` with assertion matrices) for exactly one number this PR needs to check. The plain CLI's JSON output already has that number.
- **Nightly instead of per-PR.** Leaves an accessibility regression sitting on `main` for up to a day before anyone sees it, which a solo/small-PR-volume project doesn't recoup in meaningful CI-minutes saved - unlike a genuinely expensive nightly-only check (there are none of that shape in this repo today), this one is cheap enough (one browser run, two URLs) to afford per-PR.
- **Report-only (non-blocking) with a PR comment.** Would have been the right call if performance or SEO were in scope (real flakiness risk), but accessibility's determinism removes the reason to soften it. Kept as the documented fallback if that assumption ever turns out wrong in practice.
- **Auditing against a deployed URL (`https://frontdesk.jtrent.dev`) instead of a CI-local build.** Couples every PR's gate to production being up and to whatever is currently deployed, not what the PR itself changed - the CI-local `next build`/`next start` is what actually reflects the diff under review.
- **Sharing the `node` job's build artifact via `actions/upload-artifact`/`download-artifact` instead of rebuilding.** Saves perhaps 10-15 seconds of build time at the cost of a cross-job dependency (`needs:`) and two extra actions; not worth it for a build this fast, and it would make `lighthouse` depend on `node`'s success/timing rather than standing alone as its own independently-rerunnable check.
- **Auditing `/t/[token]` too.** Real, but out of scope: it shipped in 27a without this requirement attached, and retrofitting it is a decision this PR doesn't need to make to satisfy 27b's own acceptance criterion.
