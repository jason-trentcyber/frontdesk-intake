# ADR-0031: #26 auth design — database sessions, a dedicated `auth` Postgres schema, per-request membership resolution, three-layer authorization guard; amends ADR-0003 and ADR-0018

Status: decided 2026-09-14. Amends ADR-0003 (supersedes the session-storage and schema-location detail the "Prisma adapter" clause left implicit) and ADR-0018 (narrows the "unscoped surface is exactly three functions" sentence — see §4 below). Narrows #26 to 26a; 26b (queue view, request detail, approve/edit/reject, audit) is out of scope here and unaffected by this ADR. The Consequences clause "gains ... `AUTH_TRUST_HOST=true`" is superseded by ADR-0032 (`AUTH_URL` instead — `AUTH_TRUST_HOST` didn't fix the production origin bug it was meant to, and is redundant once `AUTH_URL` is set).

## Context

#26 is "web/: Auth.js, org membership guard, queue view, request detail, approve/edit/reject + audit". ADR-0003 already decided Auth.js with Google and GitHub, identities in our Postgres, and an email allow-list (`org_members`); ADR-0018 moved the adapter from Prisma to `@auth/drizzle-adapter` but never specified where Auth.js's own tables live relative to the tenant schema, what session strategy to use, or how membership gets checked on each request. Those are exactly the questions that determine whether this repo's central security property — an org can never see another org's data — extends correctly into the one part of the schema that has no `org_id` at all. Left unstated, an implementing agent picks, which is the same failure ADR-0014, ADR-0016, and ADR-0021 were all written to avoid.

Four facts, checked before deciding:

1. **Staff read other orgs' customers' PII by design** (that's what `org_members` + RLS scope, and what F10/F11 render for whoever is signed in). Revoking someone's `org_members` row is a security action, not a convenience one — it must take effect on their very next request, not at their next sign-in.
2. **This repo runs everything — `web`, `api`, the session store (Postgres) — on one k3s node.** A stateless JWT session's usual win (no database round trip on every request) buys nothing here: the database is a pod away either way, and the query is one indexed lookup.
3. **This repo is on `next@^16.3.4`.** As of Next 16, the middleware file convention is renamed `proxy.ts` (`middleware.ts` still works but is deprecated, Edge-only, and slated for removal) and `proxy.ts` runs on the **Node.js runtime by default** — the `runtime` config export that used to force a Middleware file onto Node.js is not available in a proxy file and throws if set. ([Next.js: proxy.js file convention](https://nextjs.org/docs/app/api-reference/file-conventions/proxy), [Next.js: Renaming Middleware to Proxy](https://nextjs.org/docs/messages/middleware-to-proxy).) Auth.js's own edge-compatibility guide describes a "split config" workaround — a bare `auth.config.ts` with no adapter, instantiated separately for Edge-runtime middleware, with the full adapter-backed `auth.ts` used everywhere else — for exactly the case this repo does *not* have: a non-edge-compatible adapter (`@auth/drizzle-adapter` over `pg`, here) needed inside Edge-runtime middleware. ([Auth.js: Edge compatibility](https://authjs.dev/guides/edge-compatibility).) Because `proxy.ts` already runs on Node.js by default in this repo's Next version, there is no Edge boundary to split around, and the split-config pattern would be solving a problem this deployment doesn't have.
4. **CVE-2025-29927** was a real authorization bypass: a crafted `x-middleware-subrequest` header made Next's middleware skip entirely, so any check that lived only in middleware — including an auth redirect — never ran. Datadog's analysis names self-hosted deployments running `next start` with `output: standalone` as the affected shape ([Datadog Security Labs: Understanding CVE-2025-29927](https://securitylabs.datadoghq.com/articles/nextjs-middleware-auth-bypass/)) — which is this repo's exact `web/Dockerfile` shape. The fixed versions are well behind `next@^16.3.4`, so this repo was never exposed by this specific CVE; the durable lesson it leaves is architectural, not a live vulnerability: **proxy is a routing convenience the framework itself says can run outside the main request path, not a security boundary**, and a design that puts the only authorization check there is one crafted header away from a bypass, framework bug or not.

## Decision

### 1. Session strategy: `DATABASE`, via `@auth/drizzle-adapter`

`session: { strategy: "database" }`, not the JWT default. A session is one row in `auth.sessions`, looked up on every request the adapter is asked about. Reasoning, weighed against the JWT alternative:

- **Immediate revocation matters more than the query it costs.** Removing an `org_members` row must lock a staff member out of an org's data on their very next request. A JWT session carries no server-side state to invalidate — it stays valid until it expires, however short that expiry is set — so revocation-on-demand is not something a JWT session can do at all, only approximate with a short TTL and a re-issue race. A database session's validity is a single row's existence, which is exactly the granularity `org_members` removal needs.
- **The stateless win doesn't apply on one node.** JWT sessions exist to avoid a database round trip on request-heavy, horizontally-scaled deployments. `web` and Postgres are pods on the same k3s node; the round trip a database session costs is a local network hop to a database this pod already holds an open connection pool to (`web/src/lib/db.ts`), not a meaningfully different cost than the JWT-signature verification it replaces.
- **Revisit trigger**: a remote session store, or a multi-region deployment where the database round trip actually leaves the region the request is served from. Neither is true today; this stays a database session until one is.

### 2. Auth.js tables live in a dedicated `auth` Postgres schema, not `public`

`db/src/schema/auth.ts` declares `users`, `accounts`, `sessions`, `verificationTokens` via `pgSchema("auth").table(...)`, matching `@auth/drizzle-adapter`'s `DefaultPostgresSchema` shape (verified against the adapter's own `pg.ts` source: it needs exactly these four table objects, with the adapter internally referencing `usersTable.id/email`, `sessionsTable.sessionToken/userId/expires`, `accountsTable.userId/provider/providerAccountId`, `verificationTokensTable.identifier/token/expires` — the object *shape* the adapter code touches, not literal SQL column names, which stay `snake_case` per this repo's convention). Not one table named `users` sitting among tenant tables in `public` where a future contributor could reasonably mistake it for a tenant table and reach for `org_id`.

- `frontdesk_app` gets `GRANT USAGE ON SCHEMA auth` plus `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA auth` — a custom migration, because `deploy/postgres/initdb/002-roles.sh`'s default-privilege grants only cover `public` and `pgmq` (ADR-0016), not a schema this PR introduces.
- **No RLS, no `org_id`, on any table in `auth`.** These rows are not tenant data — a Google/GitHub identity and its session are not scoped to an org; `org_members` is the join that gives an identity an org, by email, and it alone carries `org_id`.

### 3. Membership is re-resolved per request; never cached anywhere

Every authenticated request that needs an org context calls `resolveMembership(db, session.user.email)` — the existing `resolve_membership(email)` `SECURITY DEFINER` function (`db/drizzle/0003_resolvers.sql`), already wrapped in `db/src/client.ts`. `org_id` and `role` are **never** written into the Auth.js session row, a JWT, or a cookie. The Auth.js `session` callback stays thin: it copies `user.email` onto the session object and nothing else.

Caching `org_id`/`role` anywhere in the session would reintroduce, by a different name, exactly the staleness §1 chose a database session to avoid — a cached membership is stale the instant the underlying `org_members` row changes, regardless of how fresh the session token itself is. The one-query cost of `resolve_membership` per request is the price of the revocation guarantee, paid the same way the database-session choice already pays it.

### 4. Amends ADR-0018: the unscoped surface is four resolvers-worth of function, plus a schema with none of what makes something tenant data

ADR-0018 §Row-level security says: *"Every table policy stays identical and grep-able; the unscoped surface is exactly three functions that cannot list anything."* That sentence is now inaccurate on its face — `auth`'s four tables are reachable by `frontdesk_app` with no RLS and no `org_id` at all, which is a second unscoped surface the original sentence doesn't count.

**Amended wording**: *"Every table policy stays identical and grep-able; the unscoped surface is the three resolver functions plus the `auth` schema, which contains no tenant data and no `org_id`."*

This does not widen anything silently — it is a factual update to match what this ADR just decided, made explicit rather than left for a future reader to notice the sentence had quietly stopped being true. `db/src/coverage.test.ts` (§6 below) is what keeps this machine-checked rather than a claim a comment could drift out of sync with.

### 5. The guard runs in three places: `proxy.ts`, `/app/layout.tsx`, and inside every Server Action

- **`web/proxy.ts`** — cheap check: is there a session cookie at all. No database call, no membership resolution. Redirects an obviously-unauthenticated request to sign-in before it renders anything. This is the routing convenience §Context fact 4 describes — useful for UX (an unauthenticated visitor never sees a flash of a protected layout), not relied on for the actual authorization decision.
- **`/app/layout.tsx`** — the real check: `auth()` for the session, `resolveMembership()` for the org, rendered as the "not a member" page when there's no `org_members` row. This is a React Server Component running inside the main Next.js runtime on every request to anything under `/app`, not something a spoofed internal header can route around the way it routed around middleware in CVE-2025-29927.
- **Every Server Action under `/app/*`** — the same check again, independently, at the top of the action body. A Server Action is a POST endpoint Next dispatches directly; it does not re-run the layout that happens to wrap the page it was invoked from, so skipping this would leave every mutation reachable by a client that never rendered the layout at all (a hand-crafted Server Action POST, exactly the shape #114's regression test already exercises for the public form's action).

Three independent checks, not one check called three times through a shared code path that could itself be bypassed the way middleware was — the layering is the point, not a stylistic preference. (The *implementation* of "check membership" is one function, `requireMembership()`; what makes this three layers is that `proxy.ts`, the layout, and each Server Action each independently invoke a real check rather than trusting an upstream layer to have already done it.)

### 6. `db/src/coverage.test.ts` keeps `NON_TENANT_TABLES` at `["orgs"]`, exactly

Trap already known before writing code: the coverage test iterates every table exported from `db/src/schema/index.ts` and asserts `org_id` + RLS + a policy on anything not in `NON_TENANT_TABLES`, and separately asserts `NON_TENANT_TABLES` **equals** `["orgs"]` — an exact-equality check, not "at least". Appending `"users"`/`"accounts"`/`"sessions"`/`"verificationTokens"` to that list would make it pass for the wrong reason and quietly widen what the allow-list means (from "the one non-tenant table" to "whatever's convenient"), which is exactly the drift the amended ADR-0018 sentence above is trying to keep from happening silently. Instead: `NON_TENANT_TABLES` stays `["orgs"]`; a new, separate, explicit test partitions every exported table by its Drizzle schema (`auth` vs. unqualified/`public`) and asserts every `auth`-schema table has no `org_id` column, while every table outside `auth` and not named `orgs` still has one. Both properties — the short allow-list, and the auth-schema partition — stay machine-checked, not just documented.

### 7. Staff UI lives at a real `/app/*` URL segment, not a Next route group

A route group (`(app)`) leaves no trace in the URL — `/app/queue` and a hypothetical `(app)/queue` route to the same rendered path, but only one of them lets a reader answer "is this route authenticated?" from the URL alone, without opening the file tree. `/app` is a real, visible segment.

### 8. Out of scope for #26 entirely: the owner's allow-list management UI

Filed as a new issue, not implemented here or in 26b. It needs owner-vs-staff authorization — a second authz axis on top of the one #26 introduces (is this person a member of this org at all) — and mixing "add the first axis" with "add the second axis and the UI for it" in one issue is the same undifferentiated-scope failure ADR-0025 and ADR-0027 both found and split apart. Seeds already create the initial owner row per org (`db/src/seed.ts`); that remains the only way an owner row exists until the new issue ships.

## Consequences

- `db/src/schema/index.ts` gains an `auth.ts` export; `db/src/schema/auth.ts`'s four tables carry no `org_id`, no `.enableRLS()`, no `pgPolicy`.
- A new custom migration grants `USAGE`/`SELECT, INSERT, UPDATE, DELETE` on the `auth` schema to `frontdesk_app`, alongside the generated `CREATE SCHEMA "auth"` + `CREATE TABLE "auth"."users"` (etc.) migration `drizzle-kit generate` emits from the schema file.
- `web/src/lib/db.ts`'s existing pooled `Db` singleton (`max: 5`) is what `@auth/drizzle-adapter` is instantiated against — no second pool. Auth.js's per-request database work (one session lookup, occasionally a session/account write) is lighter than a single `resolveMembership()` call plus an org-scoped query, so it fits inside the budget that pool was already sized for.
- `deploy/chart/templates/deployment.yaml`'s web container env gains `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`/`AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET` (from the already-sealed `oauth` Secret, #6/PR #118) and `AUTH_SECRET` (from the already-sealed `auth-secret` Secret), plus `AUTH_TRUST_HOST=true` — Auth.js only trusts the `Host`/`X-Forwarded-Host` header it receives from a reverse proxy when explicitly told to (self-hosted behind `ingress-nginx`, not a platform Auth.js auto-detects); without it, callback URLs Auth.js constructs would not match the real public origin.
- ADR-0018's Status line gets one sentence added noting this ADR amends the "unscoped surface" sentence — the sentence itself is not rewritten in place (`docs/adr/README.md`: "never edit a decided ADR's decision"). Same treatment for ADR-0003's Status line, noting the session-strategy and schema-location decisions this ADR makes.

## Rejected

- **JWT sessions.** Rejected in §1: no server-side revocation, and the round-trip savings it exists for don't apply on one node holding both the app and the database.
- **Auth.js's split-config pattern** (`auth.config.ts` without the adapter, instantiated separately for Edge middleware). Solves a problem this deployment doesn't have — `proxy.ts` on Next 16 already defaults to the Node.js runtime, where the full adapter-backed config works directly. Adding the split anyway would be speculative complexity for an Edge deployment this repo has no plan to run (`deploy/chart/` targets self-hosted k3s, not an edge platform).
- **Caching `org_id`/`role` in the session (database row or otherwise), refreshed periodically.** Directly reintroduces the staleness window a database session was chosen to eliminate — "periodically" is just a slower version of the JWT-expiry approximation §1 already rejected.
- **Auth.js tables in `public`, alongside tenant tables.** Works mechanically (nothing stops `pgTable("users", ...)` living next to `requests`), but makes "does this table have `org_id`?" a question the coverage test can no longer answer by a short allow-list — every future contributor reading `public`'s table list would need to separately know which four are Auth.js's own and permanently exempt for a different reason than `orgs` is. A dedicated schema makes that distinction structural instead of a fact to remember.
- **A single shared `requireMembership()` call site, invoked once and trusted by the rest of the request.** This is the shape CVE-2025-29927 broke when the single call site was "middleware runs first." Three independent invocations cost three cheap queries per request-to-a-mutation, in exchange for no request path that reaches a tenant mutation having skipped every check.
- **Building the owner allow-list UI now, since #26 already touches membership.** Rejected in §8: a second authz axis, cleanly a separate issue, and 26a doesn't need it to prove the property it's actually asked to prove.
